# API endpoint reference

This document describes the implemented backend endpoints. Example users,
passwords, dates, and tokens below are illustrative, not real credentials.

## Start the API

From the project directory:

```bash
./start_api.sh
```

Keep that terminal open. Stop the API with `Ctrl+C`.

| Address | Purpose |
| --- | --- |
| `http://127.0.0.1:8000/api/v1` | API base URL |
| `http://127.0.0.1:8000/docs` | Interactive Swagger documentation |
| `http://127.0.0.1:8000/redoc` | ReDoc reference |
| `http://127.0.0.1:8000/openapi.json` | Machine-readable API specification |

The supplied `data/astronautas.db` must exist with the `usuarios` table and
`vista_usuarios` view. Startup adds the session table if necessary.

## Endpoint summary

All paths in this table are relative to the API base URL.

| Method | Path | Authentication | Success | Purpose |
| --- | --- | --- | --- | --- |
| GET | `/health` | None | 200 | Check that the API is running |
| POST | `/auth/register` | None | 201 | Create an account |
| POST | `/auth/login` | None | 200 | Obtain an access token |
| GET | `/auth/me` | Bearer token | 200 | Read the current user's profile |
| POST | `/auth/logout` | Bearer token | 204 | Revoke the current session |
| GET | `/body-parts` | Bearer token | 200 | List available body regions |
| POST | `/measurements` | Bearer token | 201 | Save a batch of readings |
| GET | `/measurements?days=7` | Bearer token | 200 | Retrieve paginated history |
| GET | `/measurements/daily?days=7` | Bearer token | 200 | Retrieve stored daily means |
| GET | `/measurements/analytics?days=7` | Bearer token | 200 | Retrieve period statistics and daily coverage |

## Postman setup

1. Create a Postman environment with `base_url` set to
   `http://127.0.0.1:8000/api/v1` and an empty `access_token` variable.
2. Use URLs such as `{{base_url}}/auth/register`.
3. For registration and login, choose **Body → raw → JSON**. Send
   `Content-Type: application/json` and choose **Authorization → No Auth**.
4. Log in and copy the response's `access_token` into the environment variable.
5. For `/auth/me` and `/auth/logout`, choose **Authorization → Bearer Token**
   and enter `{{access_token}}` as the token.

To save the login token automatically, add this script to the login request's
**Scripts → Post-response** tab:

```javascript
if (pm.response.code === 200) {
    pm.environment.set("access_token", pm.response.json().access_token);
}
```

## GET /health

Request: `GET {{base_url}}/health`. No request body or authentication.

Response: **200 OK**.

```json
{
  "status": "ok"
}
```

This checks application liveness; it is not a database connectivity check.

## POST /auth/register

Request: `POST {{base_url}}/auth/register`. No authentication.

```json
{
  "nombre_usuario": "astronaut",
  "password": "example-password-change-me",
  "email": "astronaut@example.com",
  "fecha_nacimiento": "1995-05-21"
}
```

| Required field | Type | Validation |
| --- | --- | --- |
| `nombre_usuario` | string | 3–64 ASCII letters, digits, or underscores |
| `password` | string | 12–128 characters; sent unchanged to the server |
| `email` | string | Valid email address, at most 254 characters |
| `fecha_nacimiento` | string | Valid `YYYY-MM-DD` calendar date, no later than today in UTC |

Unknown fields are rejected. New usernames and emails are stored in lowercase.
Username and email uniqueness checks are case-insensitive. Registration does
not log the user in; call `/auth/login` afterwards.

Response: **201 Created**, with the public profile:

```json
{
  "id_usuario": 1,
  "nombre_usuario": "astronaut",
  "email": "astronaut@example.com",
  "fecha_nacimiento": "1995-05-21",
  "edad": 31,
  "creado_en": "2026-11-14T12:00:00Z"
}
```

`id_usuario` and `creado_en` are generated by the database. `edad` is calculated
by `vista_usuarios` at query time and changes with the current date. Passwords
are stored as salted Argon2id hashes; neither passwords nor hashes appear in
the response.

Errors:

| Status | Meaning |
| --- | --- |
| 409 | Username or email is already registered |
| 422 | Missing field, invalid value, malformed JSON, or unknown field |

## POST /auth/login

Request: `POST {{base_url}}/auth/login`. No authentication.

```json
{
  "nombre_usuario": "astronaut",
  "password": "example-password-change-me"
}
```

The username must contain 1–64 characters and the password 1–128 characters.
Username lookup is case-insensitive. Unknown fields are rejected. Email login
is not supported.

Response: **200 OK**.

```json
{
  "access_token": "<generated-access-token>",
  "token_type": "bearer",
  "expires_in": 3600
}
```

The token is an opaque random value, not a JWT. It expires one hour after login.
Only its hash is stored in the database. Each successful login creates a new
session; existing sessions remain valid until they expire or are logged out.
The response includes `Cache-Control: no-store` and `Pragma: no-cache`.

Errors:

| Status | Meaning |
| --- | --- |
| 401 | Unknown username or incorrect password; both return the same error |
| 422 | Invalid request body |

## GET /auth/me

Request: `GET {{base_url}}/auth/me`. No request body.

```http
Authorization: Bearer <access_token>
```

Replace `<access_token>` with the value returned by login, without brackets.

Response: **200 OK**, with the same public profile fields as registration:
`id_usuario`, `nombre_usuario`, `email`, `fecha_nacimiento`, `edad`, and
`creado_en`.

Error: **401 Unauthorized** if the token is missing, invalid, expired, revoked,
or associated with a user who no longer exists.

## POST /auth/logout

Request: `POST {{base_url}}/auth/logout`. No request body.

```http
Authorization: Bearer <access_token>
```

Response: **204 No Content**, with an empty body. This revokes only the supplied
session. Other sessions for the same user remain active. Clear the saved token
in Postman or the frontend after success.

Error: **401 Unauthorized** if the token is missing, invalid, expired, or already
revoked. Reusing the token after successful logout returns 401.

## Error response format

Authentication failure (**401**):

```json
{
  "detail": "Invalid or expired credentials"
}
```

This response includes `WWW-Authenticate: Bearer`.

Duplicate account (**409**):

```json
{
  "detail": "Username or email already registered"
}
```

Validation failure (**422**), for example a missing email:

```json
{
  "detail": [
    {
      "type": "missing",
      "loc": ["body", "email"],
      "msg": "Field required"
    }
  ]
}
```

Validation details vary with the failed check. Submitted values are omitted
from validation responses to avoid exposing passwords.

## Suggested manual request sequence

1. Call `/health`; expect 200.
2. Register a new username and email; expect 201.
3. Repeat registration; expect 409.
4. Log in with the registered credentials; expect 200 and save the token.
5. Call `/auth/me` with that token; expect 200 and the user's profile.
6. Log out with that token; expect 204.
7. Call `/auth/me` again with the same token; expect 401.

Measurement collection, history, daily summaries, and analytics are documented below. Baseline-management endpoints are not implemented yet.

## Data collection, history, and analytics

Start with `./start_api.sh`. Base URL: `http://127.0.0.1:8000/api/v1`.
Every endpoint below requires `Authorization: Bearer <access_token>` from login.
Requests cannot select another user: ownership comes from the token.

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/body-parts` | Available `id_parte` and `nombre` values |
| POST | `/measurements` | Store a batch of raw readings |
| GET | `/measurements?days=7` | Paginated history |
| GET | `/measurements/daily?days=7` | Stored daily arithmetic means per body region |
| GET | `/measurements/analytics?days=7` | Period means, ranges, movement fraction, and day coverage |

### Collection

In Postman select Body → raw → JSON and `Content-Type: application/json`.
Fetch `/body-parts` first; use the actual IDs it returns.

Example (replace the timestamp with the actual measurement time):

```json
{
  "measurements": [
    {
      "id_parte": 1,
      "timestamp": "2026-11-14T12:00:00Z",
      "temperatura": 32.5,
      "caudal": 10.2,
      "movimiento": 1
    }
  ]
}
```

Each batch contains 1–1000 readings. Regions can arrive separately or together.
Timestamps must include a timezone and cannot be in the future; storage uses UTC.
Temperature is in Celsius. Flow values are retained in the device's unit without
conversion; the unit is currently unspecified. `movimiento` is 0 or 1, where 1
means movement detected. Numeric values must be finite. No physiological ranges
are imposed yet. Unknown JSON fields, including `id_usuario`, are rejected.

Success: 201, `{"created": 1, "ids": [1]}`. Each submission appends readings;
retrying a successful request creates additional samples. Batches are atomic:
an unknown body part returns 422 and none of the batch is stored.

### Last X days and pagination

`days` defaults to 7 and accepts 1–3650. It counts UTC calendar days, including
today: `days=1` means today from midnight until the request time, rather than a
rolling 24-hour period. Responses include `from` and `to` timestamps.

All history/summary endpoints accept optional `id_parte` to select a region.
Raw history also accepts `limit` (1–1000, default 100) and `offset` (default 0).
Rows are newest first, with `id_registro` breaking timestamp ties.

Example: `/measurements?days=30&id_parte=1&limit=100&offset=0`.
History returns `total`, `limit`, `offset`, and `items`. Each item contains
`id_registro`, `id_usuario`, `id_parte`, `timestamp`, `temperatura`, `caudal`,
and `movimiento`. Empty results have `total: 0` and `items: []`.

### Stored arithmetic means

`/measurements/daily` returns `items`, ordered by date and region. Each item has:

- `id_usuario`, `id_parte`, `fecha` (UTC date).
- `muestras`: number of samples contributing to both means.
- `temperatura_media`, `caudal_media`: sum of values divided by sample count.
- `movimiento_unos`: number of readings with movement detected.

These summaries are persisted in the added `resumenes_diarios` table. Raw
readings remain in `registros`. Ingestion updates the affected daily summaries
in the same transaction, including readings submitted for earlier days. Existing
records are backfilled on startup. Direct database edits/imports require a server
restart to refresh stored summaries. Baseline tables are not modified.

Means are per region and sample-weighted, not time-weighted. A day with more
samples contributes more to a period mean. Missing days are not treated as zero.
Repeated uploads are counted as additional samples.

### Analytics useful for longer histories

`/measurements/analytics` returns `days`, `from`, `to`, and `items`, one item per
region with data. Calculations use all matching raw samples, not just one page:

- `muestras`: total readings.
- `temperatura_media`, `temperatura_min`, `temperatura_max`.
- `caudal_media`, `caudal_min`, `caudal_max`.
- `movimiento_unos`, `movimiento_fraccion` (movement readings / all readings).
- `dias_con_datos`, `dias_sin_datos`, `cobertura_dias_fraccion`.

Coverage means days with at least one sample divided by requested days. It does
not measure continuous sensor availability. Regions with no samples are omitted;
combine with `/body-parts` to show these as no data in the frontend. Movement
fraction describes samples with movement, not time spent moving.

Useful follow-up analyses include hourly patterns, baseline-relative trends,
variability, cross-signal correlations, and sampling gaps. These are not yet
implemented. They require agreed units, a sampling cadence, and enough data to
interpret reliably. Descriptive summaries here do not infer clinical conditions.

### Errors

- 401: missing, invalid, revoked, or expired bearer token.
- 422: invalid measurement, unknown body part on ingestion, or invalid query.
- Invalid bodies use the existing `detail` validation response format.

No measurement update, delete, latest-reading, or baseline-management endpoints
are included in this iteration.
